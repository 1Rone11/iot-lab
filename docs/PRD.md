# 产品需求文档（PRD）

- 产品名称：FieldLab IoT
- 文档版本：v1.1
- 日期：2026-10-29
- 状态：开发基线
- 项目性质：技术验证 / 演示系统；全部设备数据为模拟数据

## 1. 产品背景与目标

### 1.1 背景

开发者具备约 4.5 年前端经验，以 Vue / TypeScript 为主，接触过 Node.js、Electron、ECharts、MQTT 与 WebSocket，希望进入苏州工业互联网、物联网平台或工业软件研发岗位，并系统补齐 JavaScript、TypeScript、后端、SQL、桌面端、测试、部署和运维能力。

### 1.2 产品目标

1. 建立可通过浏览器公开访问的项目主页与设备控制台。
2. 用同一套 Vue 3 + TypeScript 核心界面输出 Web 和 Electron 两种客户端，不维护两套重复 UI。
3. 通过完整设备数据链路学习 JavaScript、TypeScript、Node.js、Express、SQL、MQTT、WebSocket 与 Electron。
4. 实践测试、运行时校验、权限、日志、部署、监控、备份和故障排查。
5. 通过代码、技术文档、演示视频和部署说明体现可复现的工程实现。
6. AI 故障助手为后置增强，不阻塞核心链路交付。

### 1.3 成功标准

- 本地可依据文档启动核心服务。
- 模拟设备数据通过 MQTT 到达服务端，完成校验、持久化并实时显示。
- Web 和 Electron 的设备列表、详情、趋势与告警主要业务界面来自同一个 `apps/client`。
- Electron 有至少两项真正的桌面能力，例如系统通知、受控 CSV 导出、应用版本或本地诊断日志。
- 项目包含自动化测试、数据库迁移、结构化日志、故障排查和备份恢复流程。
- 个人网站通过 HTTPS 公开展示；PostgreSQL 与 MQTT Broker 不直接暴露公网。
- 开发者能够不依赖 AI 输出，独立讲清系统架构、关键设计、失败场景和取舍。

## 2. 用户与场景

### 2.1 用户

- 开发者本人：学习、编码、调试和记录工程实践。
- 技术评估者：浏览项目主页、查看技术文档、试用演示。
- 演示访客：查看明确标注为模拟数据的只读设备信息。

### 2.2 核心场景

1. 访客打开个人网站，阅读项目目标、架构和技术决策。
2. 浏览器访客进入控制台，查看设备状态、趋势与告警。
3. 模拟器发布设备数据，后端执行校验、入库、状态更新和告警规则。
4. 用户通过客户端查看告警并记录处理过程。
5. Electron 客户端连接同一远程服务，展示桌面通知并执行受控 CSV 导出。
6. 后续版本允许用户基于模拟手册查询故障码，获得附带来源的辅助建议。

## 3. 产品架构与边界

### 3.1 唯一客户端原则

- `apps/client` 是唯一 Vue 应用，包含项目主页和设备控制台。
- Web 构建为静态资源，由 Nginx 托管。
- Electron 加载同一客户端构建产物。`apps/desktop` 只负责 main、preload、IPC、安全策略和打包，不维护第二份 Vue 页面。
- 通过平台能力适配层区分浏览器与桌面能力；核心页面、数据模型和 API client 共用。
- Web 同源使用 `/api` 与 WSS；Electron 的 API base URL 由安全 preload 运行配置提供，不包含任何服务端密钥。

### 3.2 不做的事

- 不接真实工厂设备、不控制真实设备。
- 不开发 PLC 程序、驱动、固件或完整工业协议栈。
- 不拆分微服务，不使用 Kubernetes。
- 不在 2 GiB 服务器运行本地大模型。
- 不允许 AI 自动执行设备控制、删除数据或任意 SQL。
- 不允许 Web / Electron 各维护一套复制的设备管理 UI。

## 4. 功能范围

### 4.1 MVP：必须实现

- 项目主页：项目说明、技术栈、架构图、功能截图、源码 / 文档链接、模拟数据说明。
- 共享 Vue 客户端路由：项目主页与设备控制台至少两个区域。
- 设备模拟器：至少 3 台逻辑设备，每 3–10 秒上报一组测点；可模拟运行、告警、离线和异常值。
- MQTT 接入：Topic 与 payload 契约、运行时校验、重连、消息 ID 去重。
- Node.js / Express API：健康检查、设备列表、详情、历史测点、告警查询与状态更新。
- PostgreSQL：版本化迁移、约束、分页查询、候选索引与种子数据。
- 控制台：设备列表、状态、实时指标、历史趋势、告警列表与详情。
- WebSocket：推送设备状态和告警变化；重连后重新请求 REST 快照。
- 基础可靠性：结构化日志、请求 ID、统一错误处理、健康检查。
- 基础安全：参数校验、演示访问策略、速率限制、密钥不进入仓库。
- Docker Compose 部署；PostgreSQL 与 Mosquitto 使用内部网络。

### 4.2 Electron 阶段：必须实现

- Electron 使用 `apps/client` 的同一渲染界面，不复制核心业务页面。
- 明确 main / preload / renderer 责任边界。
- 默认 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。
- preload 用 `contextBridge` 暴露最小类型化接口，不暴露原始 `ipcRenderer`。
- Electron 通过 HTTPS / WSS 访问服务端，不直接连接数据库或 MQTT Broker。
- 完成至少两项桌面能力：系统通知、受控 CSV 导出、应用版本信息、本地诊断日志任选至少两项。
- 提供至少一个目标操作系统的安装包，并记录构建与启动测试。

### 4.3 后续增强

- 登录与 RBAC：区分只读演示用户和管理员；所有写操作在服务端授权。
- 告警状态机：确认、关闭、备注和操作历史。
- CI：lint、类型检查、测试和构建。
- AI 故障助手：模拟手册检索、带引用回答、只读历史数据工具、评测问题集。
- 更完整的项目演示视频、ADR、性能记录和备份恢复记录。

## 5. 功能需求与验收

### FR-01 设备模拟器

- 设备有唯一 `deviceId`、名称、类型与状态。
- 测点消息包含 `messageId`、`reportedAt`、测点名称、值、单位和设备状态。
- 支持正常、告警、离线、异常值模拟。
- 验收：运行 10 分钟后可以查询到新数据；停止单台设备后，系统可在配置阈值内将其判定为离线。

### FR-02 MQTT 消息接入

- API consumer 订阅 Topic，对 payload 做运行时校验。
- Topic 中的设备 ID 必须与 payload 的设备 ID 一致。
- 用唯一约束或 ingestion 表实现幂等处理。
- 验收：重复投递不造成重复测点；非法 JSON 不导致服务崩溃；Broker 重启后客户端可重新连接和订阅。

### FR-03 API 与数据库

- 支持设备分页、设备详情、时间范围测点查询和告警查询。
- 所有输入经过校验，时间范围、分页大小和 payload 大小均有限制。
- 数据结构通过迁移创建，不靠手工修改线上数据库。
- 验收：正常、无数据、非法参数、未知设备和依赖不可用均有可预测响应与测试。

### FR-04 共享控制台

- Web 和 Electron 展示同样的设备列表、详情、指标、历史趋势和告警主要 UI。
- WebSocket 消息经过校验；断线后重新连接并拉取 REST 快照。
- 组件卸载时清理监听器、定时器与 ECharts 实例。
- 验收：切换路由不会重复订阅；断网恢复后状态能够重新同步；两种运行目标的核心业务行为一致。

### FR-05 平台适配层

- Vue 页面只依赖项目定义的平台能力接口，不直接访问 Electron API。
- Web 使用浏览器能力或明确的降级提示；Electron 使用 `window.fieldlabDesktop` 白名单接口。
- API base URL 按运行目标正确配置，不能把密钥写进客户端。
- 验收：浏览器构建中没有 Electron / Node.js 特权模块；桌面桥接不可用时页面不会因访问未定义对象而崩溃。

### FR-06 Electron 桌面壳

- 通过同一共享客户端构建产物启动，不拥有第二套 Vue 页面。
- 实现桌面通知和受控 CSV 导出等桌面能力。
- 校验 IPC 参数、调用来源、文件名和数据大小；限制导航、弹窗与外链。
- 验收：桌面端能启动、访问设备列表、显示新告警通知并导出数据；非法 IPC 参数无法任意读写文件或执行命令。

### FR-07 部署和公开演示

- Nginx 提供项目主页页面与 Web 控制台；API / WSS 通过反向代理访问。
- Electron 安装包在本地构建，并可通过项目主页页面链接到发布下载位置。
- PostgreSQL、MQTT Broker 不直接开放公网端口。
- 验收：从公开网站能进入项目介绍和在线演示；桌面端使用文档配置的服务地址连接云端；页面清楚注明数据为模拟数据。

### FR-08 AI 故障助手（可选）

- 仅检索项目模拟手册和有权限访问的历史数据。
- 回答返回引用来源；资料不足时说明无法确定。
- AI 工具只读，设输入长度、超时、调用量与成本限制。
- 验收：至少用 20 个问题人工评估，并记录有据、缺证、错误和拒答案例。

## 6. 非功能需求

- 可维护：TypeScript strict；模块边界清晰；避免无边界 `any`。
- 可靠：外部依赖有超时、失败处理、有限重试与健康检查。
- 安全：最小开放端口、环境密钥隔离、服务端授权、日志脱敏。
- 性能：列表分页、历史查询限范围、图表限窗口、避免无界缓存。
- 可测试：消息校验、告警规则、共享 API client 和平台能力有独立测试。
- 可部署：开发、测试、线上配置分离；Electron 在本地构建，云端只运行服务端与 Web 静态资源。
- 可演示：公开站点提供架构、演示说明、源码 / 文档和已知限制。

## 7. 技术与容量约束

- 云服务器：Ubuntu 22.04 64 位、2 vCPU、2 GiB RAM、40 GiB ESSD Entry。
- 优先轻量常驻服务；不在服务器跑本地大模型；控制模拟频率、日志、连接池与历史数据保留量。
- 先采用模块化单体，避免提前拆微服务。
- Electron 原生能力通过 preload + IPC 白名单提供。
- 所有设备与历史测点均为模拟数据，项目主页中须明确说明。

## 8. 风险与缓解

| 风险 | 缓解方案 |
|---|---|
| 项目范围过大 | 先打通设备数据链路，再加 Electron 桌面能力，最后考虑 AI |
| 双端导致代码重复 | 唯一共享客户端 `apps/client`；Electron 只保留 main/preload/IPC/打包 |
| Electron 安全边界不清 | 默认安全配置、最小 preload API、测试非法 IPC 参数 |
| 2 GiB 内存不足 | 本地构建、轻量容器、限流与数据保留、观察资源指标 |
| AI 代码不可理解 | AI 只辅导；开发者独立设计、编码、测试与解释 |
| 模拟项目看起来不真实 | 清楚标注模拟数据，突出工程问题、测试、故障恢复和决策记录 |
